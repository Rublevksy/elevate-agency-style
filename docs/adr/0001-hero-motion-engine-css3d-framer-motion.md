# Hero motion engine: чистый CSS 3D + Framer Motion, без Three.js

## Контекст

Бриф ставит «PREMIUM VISUALS + SMOOTH 60FPS FEEL + FAST LOAD + MOBILE
PERFORMANCE» выше буквального 3D-рендера (R81), а scroll-сцена hero должна
быть одной связной последовательностью с единым источником состояния, не
набором независимых анимаций (R39). В проекте уже есть рабочий прецедент
чистого CSS-3D — `Hero3DCube.tsx`, и `framer-motion` уже в зависимостях.

## Решение

Hero-сцена (`DeviceHero`) реализована на чистом CSS 3D (`perspective` +
`rotateX/Y/Z` на слоях `div`/`svg`) и Framer Motion: один `scrollYProgress`
через `useScroll`/`useTransform` управляет `translateY`/`rotateX`/`rotateY`/
`scale` MacBook, opacity фоновых слоёв и кроссфейдом контента экрана.
Three.js/WebGL в проект не добавляется.

## Почему

Рассматривалась и отклонена связка с Three.js/WebGL — типичный выбор для
«cinematic 3D device» на маркетинговом сайте. Она добавляет тяжёлую
библиотеку, риск просадки FPS на мобильных и сложность SSR/гидратации для
первого экрана — это прямо противоречит приоритету R81 (perf важнее
буквальности 3D-рендера) и требованию R39.1 (валидный статичный первый кадр
без ожидания гидратации JS). CSS-3D + Framer Motion уже имеет рабочий
прецедент в кодовой базе (`Hero3DCube.tsx`) и остаётся в рамках
`transform`/`opacity` — единственных performant-свойств для scroll-driven
анимации (R82/R83).

## Последствия

Устройство никогда не станет «настоящим» 3D-объектом с реальной геометрией и
расчётом освещения от рендер-движка — глубина и rim-light — это иллюзия через
`box-shadow`/градиенты и perspective-трансформы слоёв, а не физический свет.
Сложные ракурсы (свободное вращение камеры, произвольная 3D-перспектива)
недостижимы без будущей миграции на WebGL-движок. Любое будущее решение
«добавить полноценный 3D-рендер» потребует переписать `DeviceHero` с нуля, а
не доработать существующий.
